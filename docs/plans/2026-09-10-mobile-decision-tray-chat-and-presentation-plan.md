# 러브레터 모바일 결정 영역·채팅·행동 템포 구현 계획

작성일: 2026-09-10  
상태: 구현 전 계획 확정  
대상: 현재 React 18 기반 Love Letter v2 게임 화면

## 1. 목표

모바일 게임 화면을 실제 카드 테이블처럼 이해하기 쉽고, 오른손 한 손 조작에 적합하게 재배치한다.

이번 작업의 결과는 다음 조건을 만족해야 한다.

1. 내 손패는 화면 하단 오른쪽에 배치한다.
2. 손패 왼쪽에는 실제 카드 한 장 크기의 행동 칸 하나만 둔다.
3. 사용 카드와 확인 카드는 하나의 행동 칸에서 상태에 따라 포개어 보여준다.
4. 상대 손패 뒷면은 확보된 공간에 맞춰 더 크게 표시한다.
5. 내 탈락 상태는 빈 행동 칸 주변이 아니라 하단 결정 영역 자체에서 명확히 보여준다.
6. 채팅을 열고 모바일 키보드가 올라와도 배경 게임판은 원래 위치를 유지한다.
7. 채팅 헤더에 닫기 버튼을, 입력창 옆에 명확한 전송 버튼을 둔다.
8. 로컬 사용자를 가리키는 표현은 `나`, `내`, `나의`로 통일한다.
9. 행동 결과는 다음 턴으로 넘어가기 전에 최소 3초간 읽을 수 있어야 한다.

- 관련 프레젠테이션 상태와 좌표 측정
- 반응형·접근성·브라우저 검증

## 3. CURRENT BEHAVIOR

현재 내 영역은 공개 패와 두 칸짜리 행동 영역을 손패 위에 배치한다.

```text
[내 공개 패]          [사용 위치][확인 위치]

               행동 안내와 버튼

                    [손패 1][손패 2]
```

이 구조에서는 다음 문제가 발생한다.

- 행동 영역이 카드 두 장 너비이므로 큰 빈 점선 사각형으로 보인다.
- 행동 버튼과 행동 영역의 세로 공간이 겹친다.
- 손패가 화면 가운데에 있어 오른손 엄지의 이동 거리가 길다.
- 내 탈락 문구가 행동 영역 아래 절대 위치에 붙어 맥락이 불명확하다.
- 상대 손패 뒷면이 `18.9 × 27px`로 너무 작다.
- 결과 문구가 마지막 정리 단계에서 짧게 나타난 후 사라진다.
- 채팅 패널과 닫기 버튼이 각각 고정되어 닫기 버튼이 입력창을 덮는다.
- 키보드가 나타날 때 `dvh` 기반 게임판 높이도 바뀌어 배경 배치가 재계산된다.
- `나`, `내`, 닉네임, `플레이어`가 같은 사용자를 가리키는 문구 안에서 섞인다.

## 4. ROOT CAUSE

### 4.1 하단 게임 영역

`PlayerZone.tsx`의 `LocalObjects`가 공개 패와 `SelfTarget`을 같은 행에 배치한다. `SelfTarget` 안의 `PlaySpace`와 `ReviewSpace`는 서로 다른 크기로 나란히 존재한다. 탈락 상태인 `SelfState`는 이 컨테이너의 아래쪽 바깥에 절대 위치한다.

### 4.2 카드 애니메이션 좌표

`SpatialMotionStage.tsx`는 `play`와 `review`를 별개의 도착 좌표로 측정한다. 현재 UI는 이 내부 좌표를 그대로 두 개의 점선 칸으로 노출한다. 그러나 좌표가 두 개여야 한다는 사실과 화면에 두 칸이 보여야 한다는 것은 별개의 요구다.

### 4.3 행동 결과 수명

`physicalSequence.ts`에는 짧은 `HOLD`와 `CLEANUP` 단계만 있다. `ActionStage.tsx`는 결과 문구를 주로 `CLEANUP`에서 보여주므로 실제 읽기 시간이 약 1초 이하로 줄어든다.

### 4.4 채팅과 키보드

`RoomChat.jsx`는 채팅 시트를 `48dvh` 높이로 만들고 화면 하단에 고정한다. 모바일 키보드가 차지한 실제 가시 영역인 `window.visualViewport`를 사용하지 않는다. 열기 버튼이 채팅이 열린 뒤 닫기 버튼으로 바뀌지만 계속 우측 하단에 남아 입력 폼과 겹친다.

## 5. DESIRED EXPERIENCE

### 5.1 행동 가능한 상태

```text
┌─────────────────────────────────────┐
│ 행동 설명 또는 결과                 │
│ [취소]                    [사용 확정]│
└─────────────────────────────────────┘

내 공개 버린 패  [카드][카드][카드]…

[ 행동 카드 칸 ] [   손패 1   ][   손패 2   ]
                  오른손 조작 영역 ───────→
```

손패가 한 장이면 오른쪽 끝 슬롯에 둔다.

```text
[ 행동 카드 칸 ] [     빈 자리 ][   손패 1   ]
```

### 5.2 탈락 상태

내가 탈락하면 선택할 카드와 행동 칸을 계속 보여주지 않는다. 같은 하단 위치에 관전 상태를 표시한다.

```text
┌─────────────────────────────────────┐
│ ⊘ 이번 라운드에서 탈락했습니다      │
│   관전 중 · 다음 라운드를 기다려 주세요 │
└─────────────────────────────────────┘
```

상대가 탈락하면 그 상태는 해당 상대의 좌석 안에서 표시한다. 아바타 상태 아이콘, 낮아진 좌석 대비, `탈락` 텍스트를 함께 사용하며 색상에만 의존하지 않는다.

### 5.3 채팅 상태

```text
┌ 채팅 ───────────────────────── [×] ┐
│ 시스템 및 사용자 메시지             │
│                                     │
├─────────────────────────────────────┤
│ 메시지 입력…              [전송 ➤] │
└─────────────────────────────────────┘
────────────── 모바일 키보드 ──────────
```

게임판은 채팅을 열기 직전의 위치와 크기를 유지한다. 채팅 시트만 키보드 위의 가시 영역에 맞춰 이동하고 줄어든다.

## 6. STATE FLOW

### 6.1 일반 카드 행동

```text
사용자가 오른쪽 손패 선택
↓
로컬 interactionState 변경
↓
대상·추측 선택
↓
사용 확정 및 서버 명령 전송
↓
서버가 권위 있는 결과와 presentation 이벤트 전송
↓
선택 카드가 오른쪽 손패에서 왼쪽 행동 칸으로 이동
↓
대상 효과 연출
↓
RESULT_DWELL에서 결과를 3초간 표시
↓
카드가 공개 버린 패로 이동
↓
프레젠테이션 ACK
↓
서버 상태에 맞춰 다음 턴으로 정착
```

### 6.2 사제 확인

```text
사제 카드가 행동 칸에 놓임
↓
상대 손패가 같은 행동 칸 위쪽 레이어로 이동
↓
행동 주체에게만 앞면 공개
↓
사용자가 반환 버튼 선택
↓
확인 카드가 상대 손으로 복귀
↓
결과 확인 문구 3초 표시
↓
사제가 공개 버린 패로 이동
```

비공개 카드 값은 현재 서버의 수신자별 payload 경계를 그대로 사용한다. 레이아웃 변경을 위해 숨겨진 카드 정보를 추가로 전달하거나 DOM에 남기지 않는다.

```text
↓

↓

```

```text
↓

↓
```

## 7. VISUAL FLOW와 공간 규칙

### 7.1 로컬 결정 트레이

- 기본 열은 `행동 칸 / 손패 1 / 손패 2`의 3열이다.
- 세 열은 같은 카드 종횡비 `154 / 220`을 사용한다.
- 사용 가능한 가로 폭에 따라 세 열이 같은 비율로 축소된다.
- 손패 두 장은 가운데와 오른쪽 열을 사용한다.
- 손패 한 장은 오른쪽 열을 사용한다.
- 카드 선택 안내는 트레이 위 한 줄에 표시한다.
- 행동 버튼은 중앙 행동 설명 박스 아래에 유지하되 트레이와 별도 레이아웃 행을 차지한다.
- 버튼과 트레이 사이에 최소 12px의 실제 레이아웃 간격을 둔다.
- `position: absolute`로 버튼과 카드 영역의 관계를 맞추지 않는다.

### 7.2 단일 행동 칸

- 사용자에게 보이는 점선 테두리는 하나만 렌더링한다.
- 행동 칸의 크기는 로컬 손패 카드 한 장과 같다.
- 내부에 `play`와 `review` 앵커를 절대 위치 레이어로 둔다.
- 두 앵커의 기준 사각형은 동일하다.
- 일반 사용 카드는 아래 레이어에 둔다.
- 확인·비교 카드는 위 레이어에 둔다.
- 두 카드가 동시에 존재하면 아래 카드를 5~7px 이동하고 약간 축소해 포개진 카드임을 보여준다.
- 행동 칸은 `idle`, `receiving`, `occupied`, `reviewing`, `resolving`, `disabled` 상태를 갖는다.
- 상태 차이는 테두리 굵기, 카드 배치, 짧은 진입 모션으로 표현한다. 지속적인 발광이나 반복 펄스는 사용하지 않는다.

### 7.3 상대 영역

- 상대의 두 칸짜리 행동 영역도 점선 한 칸으로 교체한다.
- 확보된 폭은 손패 뒷면 확대에 사용한다.
- 카드 뒷면은 플레이어 수에 따라 CSS 변수로 조절한다.
  - 상대 1~2명: 약 34~38px 너비
  - 상대 3명: 약 30~34px 너비
  - 상대 4~5명: 최소 27~30px 너비
- 실제 최종 수치는 360px와 390px 화면에서 좌석 겹침이 없는 범위로 브라우저 조정한다.
- 카드 비율과 애니메이션 앵커 중심은 항상 일치해야 한다.

### 7.4 공개 버린 패

- 이전 작업에서 적용한 전체 카드 렌더링과 줄바꿈을 유지한다.
- 로컬 공개 패는 결정 트레이 위의 독립 행으로 이동한다.
- 공개 패의 높이 변화가 행동 버튼이나 손패를 덮지 않도록 정상 문서 흐름으로 배치한다.

## 8. 플레이어 호칭 규칙

로컬 사용자를 가리키는 표현은 문장 역할에 맞춰 다음처럼 통일한다.

| 문장 역할 | 로컬 사용자 | 다른 사용자 |
|---|---|---|
| 이름표 | 나 | 알렉산더 |
| 주어 | 내가 | 알렉산더님이 |
| 목적어 | 나를 | 알렉산더님을 |
| 소유 | 내 또는 나의 | 알렉산더님의 |
| 차례 | 내 차례 | 알렉산더님의 차례 |

`내`와 `나의`의 사용 원칙은 다음과 같다.

- 짧은 게임 안내와 상태: `내 차례`, `내 카드`, `내 공개 버린 패`
- 소유 관계를 강조해야 하는 설명: `나의 행동 카드`, `나의 선택`
- 버튼과 접근성 라벨: `나를 대상으로 선택`

예상 문구:

- `내 차례 · 카드를 선택하세요`
- `상대의 차례 · 내 카드를 확인할 수 있어요`
- `나를 대상으로 선택`
- `내가 남작을 사용했습니다`
- `알렉산더님이 나를 대상으로 선택했습니다`
- `내 카드가 공개되었습니다`

### 구현 방식

`playerCopy` 유틸리티를 만들고 다음 형태의 참조를 제공한다.

- `name`: 나 / 닉네임
- `subject`: 내가 / 닉네임님이
- `object`: 나를 / 닉네임님을
- `possessive`: 내 / 닉네임님의

`ActionStage`, HUD, 손패 안내, 대상 선택, 사제 확인, 탈락 결과에서 같은 유틸리티를 사용한다. 식별 가능한 플레이어를 `플레이어`라고 표시하지 않는다. 플레이어 ID나 닉네임이 정말 없는 예외 상황에서만 `상대`를 사용한다.

채팅 시스템 입장 기록은 사건 기록이므로 실제 닉네임을 유지한다. 내 일반 채팅 발신자 이름은 메시지의 사용자 ID를 확인할 수 있을 때 `나`로 표시한다.

## 9. 결과 3초 유지 설계

### 선택 접근

`PhysicalKind`에 결과 읽기 전용 단계인 `RESULT_DWELL`을 추가한다.

- 카드 이동과 대상 효과가 끝난 뒤 시작한다.
- `ActionStage`는 이 단계에서 구조화된 결과 문구를 표시한다.
- 지속 시간은 기본 3초다.
- 결과 단계가 끝난 뒤 `CLEANUP`으로 이동한다.
- 최종 ACK는 기존처럼 정리가 끝난 뒤에만 전송한다.

### 시간 기준

- 마이크로 피드백: 100~180ms
- 카드 이동: 350~700ms
- 대상 반응: 400~800ms
- 결과 읽기: 3000ms
- 공개 패 정착: 450~650ms

카드 이동을 3초로 늘리지 않는다. 읽어야 하는 결과만 3초 동안 안정적으로 유지한다.

### 예외

- 사제의 비공개 확인은 사용자가 반환하기 전까지 유지한다.
- 오류 메시지는 사용자의 다음 입력 또는 명시적 닫기 전까지 유지하되 같은 오류를 중복 표시하지 않는다.
- `prefers-reduced-motion`에서는 이동 시간을 줄이지만 결과 읽기 3초는 유지한다.
- 동일한 `actionId`가 다시 도착해도 `RESULT_DWELL`을 처음부터 반복하지 않는다.

## 10. 채팅 구현 설계

### 10.1 구조

`RoomChat`의 sheet 모드를 다음 구조로 나눈다.

- `ChatLauncher`: 닫힌 상태의 우측 하단 원형 버튼
- `ChatPortal`: `document.body`에 렌더링되는 오버레이
- `ChatSheet`: 헤더, 메시지 피드, 입력 폼
- `ChatHeader`: 제목과 닫기 버튼
- `ChatComposer`: 입력창과 전송 버튼
- `useVisualViewportRect`: 모바일 가시 영역 측정 훅

### 10.2 배경 게임판 고정

- 채팅을 열 때 현재 게임 화면의 CSS 높이를 기록한다.
- 채팅이 열린 동안 키보드 resize로 게임판 높이를 다시 계산하지 않는다.
- 게임판은 시각적으로 원래 위치에 남는다.
- 배경 포인터 입력과 스크롤을 차단한다.
- 채팅이 닫힌 뒤 높이 고정을 해제하고 현재 방향에 맞춰 한 번 재측정한다.

### 10.3 키보드 대응

`window.visualViewport`의 다음 값을 사용한다.

- `height`
- `offsetTop`
- `offsetLeft`

`resize`와 `scroll` 이벤트를 듣고 `requestAnimationFrame` 단위로 시트 위치를 갱신한다. 시트는 가시 영역의 위아래에 8~12px 여백을 둔다.

`visualViewport`를 지원하지 않는 브라우저에서는 `window.innerHeight`를 사용한다.

### 10.4 컨트롤

- 닫기 버튼: 헤더 우측, 최소 `40 × 40px`
- 전송 버튼: 입력창 우측, 최소 높이 `44px`
- 전송 버튼 문구: `전송`
- 전송 중인 상태가 필요하면 `전송 중…`과 disabled 상태 제공
- 입력값이 비어 있으면 전송 버튼 disabled
- Enter 전송을 유지하고 모바일 IME 조합 중에는 제출하지 않음
- 메시지 피드만 스크롤
- 헤더와 입력 폼은 항상 화면에 남음
- 입력 폼에 안전 영역 하단 여백 적용

## 12. 구현 단계와 완료 기준

## 14. 위험과 대응

### 한 슬롯에 여러 카드가 완전히 겹치는 문제

카드 역할별 z-index와 작은 오프셋을 프레젠테이션 상태에서 계산한다. 카드 값이나 소유권을 복제하지 않는다.

### 하단 3열이 좁은 화면에서 넘치는 문제

세 칸 모두 하나의 CSS 카드 폭 변수를 공유하고 컨테이너 폭에서 역산한다. 임의로 한 요소만 축소하지 않는다.

### 공개 패 증가로 하단 영역이 밀리는 문제

공개 패는 최대 높이 이후 내부 줄바꿈 또는 세로 공간 정책을 명시한다. 손패와 행동 슬롯의 최소 터치 영역을 먼저 보존한다.

### 3초 표시가 다음 플레이어 시간을 소비하는 문제

서버 프레젠테이션 ACK 이전에 결과 읽기 단계를 수행한다. 새 턴의 제한시간이 시작된 뒤 클라이언트만 기다리는 구조는 허용하지 않는다.

### 채팅 키보드 동작의 브라우저 차이

`visualViewport` 우선, `innerHeight` 대체 경로를 제공한다. Android Chrome 실기기 확인을 최종 수용 조건에 포함한다.

### 호칭의 조사 오류

문장 전체를 단순 문자열 결합하지 않고 주어·목적어·소유격 형태를 포매터에서 제공한다.

## 15. 최종 수용 조건

- 내 행동 칸은 손패 왼쪽에 있으며 실제 카드 한 장 크기다.
- 내 손패 한 장은 오른쪽 끝, 두 장은 가운데와 오른쪽에 배치된다.
- 행동 버튼과 행동 칸은 어떤 지원 화면에서도 겹치지 않는다.
- 화면에 `사용`과 `확인` 점선 칸이 따로 나타나지 않는다.
- 사제·남작·국왕 연출이 단일 슬롯 구조에서도 이해 가능하다.
- 상대 카드 뒷면이 현재보다 명확히 커지고 좌석을 침범하지 않는다.
- 내 탈락 상태가 하단 관전 영역에 표시되고 빈 행동 칸은 사라진다.
- 로컬 사용자 호칭은 `나 / 내 / 나의` 문법으로 일관된다.
- 식별 가능한 상대는 실제 닉네임으로 표시된다.
- 행동 결과는 최소 3초간 안정적으로 표시된다.
- 채팅 키보드가 열려도 배경 게임판 좌표가 유지된다.
- 채팅 입력창, 전송 버튼, 닫기 버튼이 키보드 위에 모두 보인다.
- 서버 권위 상태와 비공개 카드 보호가 유지된다.
- 전체 테스트, 타입 검사, 빌드, 모바일 브라우저 검증이 통과한다.
